# CLAUDE.md

clipsync shares the clipboard between Linux (Wayland) and Android devices over the LAN, peer to peer. Start with
`handbook/README.md` for how the project works today.

## Working Boundaries

- Do not edit files outside this project's root directory.
- Do not install anything on the system (`cargo install`, `rustup component add`, `pip install`, system packages)
  without asking first. Throwaway tools may be built inside a scratch directory that is deleted afterwards.
- `clipsyncd watch` / `set` and the Wayland backend act on the real clipboard of the running desktop session. Say so
  before a manual test. Use an isolated clipboard session when one is available; otherwise preserve and restore the
  desktop session's contents using the procedure and limitations in `handbook/DEVELOPMENT.md`. A plain `wl-paste`
  backup does not preserve every offered MIME type or metadata.
- Follow Publication and Authorization below for all remote Git actions.

## Stack

These are the intended architecture and tooling, including decisions for components not built yet. See `README.md`
for implementation status and `handbook/ARCHITECTURE_DECISIONS.md` for the reasoning behind these choices.

- Platforms: Linux with a Wayland compositor that supports data-control (`ext-data-control-v1` or
  `wlr-data-control-unstable-v1`), and Android 10 (API 29) or newer.
- Protocol core, shared by both platforms: Rust (`clipsync-core`), with `serde_json` for messages, `sha2` for
  digests and `url` for pairing URIs.
- Linux daemon and CLI: Rust.
  - Clipboard: `wayland-client`, `wayland-protocols` and `wayland-protocols-wlr`, with a `calloop` event loop.
  - Async runtime: tokio.
  - TLS: rustls.
  - LAN discovery: `mdns-sd`.
  - Certificates: `rcgen` to issue, `x509-parser` to read; `ring` as the crypto provider.
  - CLI parsing: `clap`. Logging: `tracing`. QR codes in the terminal: `qrcode`.
  - Desktop notifications: `notify-rust` (D-Bus).
  - Service: systemd user unit.
- Android app: Kotlin.
  - Protocol logic: `clipsync-core` through Kotlin bindings generated by UniFFI, native library built with
    `cargo-ndk`.
  - UI: Jetpack Compose with Material 3.
  - TLS: JSSE/Conscrypt.
  - Key storage: Android Keystore.
  - LAN discovery: `NsdManager`.
  - QR codes: ZXing.
- Testing: `cargo test` and JUnit; coverage with `cargo llvm-cov`; diff coverage with `diff-cover`.
- Dependency audit: `cargo-deny`.
- Style: `rustfmt` and `clippy`; `ktlint` and Android Lint.
- Do not add: Flutter or another cross-platform UI layer; a second implementation of the protocol logic in Kotlin
  (see D2 in `handbook/ARCHITECTURE_DECISIONS.md`); Google ML Kit or other proprietary Play Services libraries
  (they block F-Droid).

## Distribution

Intended distribution channels; this list does not imply that packages or releases are available.

- Linux: an AUR package and release binaries on GitHub.
- Android: APK on GitHub releases and on F-Droid.

## Engineering Principles

- Practice Extreme Programming (XP): Test-Driven Development, continuous refactoring, and small releases.
  - TDD: every feature starts with a failing test, and the implementation is written only to make that test pass.
    For protocol behaviour the failing test is a new known-answer case in `clipsync-core`'s `tests/spec.rs`.
  - Continuous refactoring: make refactorings needed for the change and small, directly related improvements, in
    steps kept green by the test suite. Propose larger or unrelated refactorings separately.
  - Small releases: ship small, independently mergeable changes instead of large batches, so each one is easy to
    review, verify, and roll back.
- `spec/protocol.md` is the source of truth for the protocol. Its deterministic rules are pinned by known-answer tests
  in `clipsync-core`'s `tests/spec.rs`, whose expected values are literals: never derive them from the code under
  test.
- The protocol logic is written once, in `clipsync-core`, and shared: the Linux daemon links it directly and the
  Android app calls it through UniFFI (D2). Kotlin holds only platform code: TLS and the Keystore, NSD, the
  foreground service, the clipboard and the UI.
- A protocol change updates, in the same change: `spec/protocol.md`, `tests/spec.rs` and `clipsync-core`.
- `clipsync-core` stays sans-IO: no sockets, clocks, threads or clipboard access. Each host does its own I/O and feeds
  bytes and events in, which keeps TLS keys inside the Android Keystore and lets the core be tested as plain
  functions.
- The public API of `clipsync-core` stays FFI-friendly: plain data types and enums across the boundary, errors as
  enums, no generics or lifetimes in exported items, synchronous calls, no I/O callbacks.
- Peer to peer only: devices talk directly, one daemon plus one CLI per Linux machine, with no server or cloud
  component.
- Dependencies must have licences compatible with distributing clipsync under MIT (permissive licences only). The one
  exception is UniFFI's crates (MPL-2.0, see D2), used unmodified. `cargo-deny` enforces this for Rust and checks
  RustSec advisories and crate sources.
- The Wayland backend runs its event loop on a dedicated thread; offer reads and paste serving run on short-lived
  threads. Never read an offer that carries our own marker MIME type: this process serves it, so it would deadlock.
- Add automated tests appropriate to each behaviour change, including code that needs a compositor, the network or
  a phone. Depending on the behaviour, use an in-memory clipboard backend, a headless compositor (Sway with
  `WLR_BACKENDS=headless`), or a local peer; add the required harness when it does not exist. These are testing
  strategies, not a claim that all harnesses are implemented or run in CI. Manual testing complements automated
  tests; it does not replace them.
- Report which checks ran and their results, and identify checks that could not run and why. Never report an
  unexecuted check as passed.

## Design Guidelines

These apply to the Android app's user interface.

- Modern and responsive: Material 3 in Compose with dynamic colour, light and dark themes, phones and tablets in both
  orientations, and layouts that survive the largest system font size.
- Whenever a screen is touched, bring it up to these criteria unless it already conforms.
- Every flow that asks for input (pairing, renaming the device, adding a manual address) has a Cancel/back action that
  returns to where it was launched from with no side effects. Cancelling a pairing sends `pair_result { ok: false }`.
- One primary action per row in lists: tapping a device opens its page; less common actions (unpair, per-device
  toggles) live on that page, not on the row.
- When images or files are synced (after v1): show a preview before sending: a thumbnail for images, the file name
  otherwise.

## Documentation

- `handbook/` mirrors what the project does today: architecture, architecture decisions, development setup, and a
  page per user-facing flow under `flows/` as flows ship. It describes only shipped behaviour; the one exception is
  `ARCHITECTURE_DECISIONS.md`, which also records decisions in force for parts not built yet.
- `spec/protocol.md` is the wire contract, written before the code that implements it. While its status is draft it
  may change freely; once frozen, any change needs a new protocol version.
- Each kind of content has one home: shipped behaviour in `handbook/`, the reasoning behind technical decisions in
  `handbook/ARCHITECTURE_DECISIONS.md`, the protocol in `spec/protocol.md`, and how to build, test and try the code in
  `handbook/DEVELOPMENT.md` (Quick Validation below repeats the everyday checks as a shortcut).
- Update the docs in the same change that alters the behaviour they describe; a change is not done while the handbook
  or the spec contradicts the code. When they disagree, don't assume either side is right: investigate which one is
  wrong.
- Docs describe the current state as if they had always been written that way: no change history ("no longer",
  "replaced", "superseded", "now"). When something changes, rewrite the affected text; git history records how it got
  there. `ARCHITECTURE_DECISIONS.md` follows the same rule: an entry states the decision in force and the alternatives
  rejected.
- Docs, code, comments, commits and pull requests are written in English.

## Quick Validation

For Rust changes, run from `linux/`:

```sh
cargo test
cargo fmt --check
cargo clippy --all-targets -- -D warnings
```

See `handbook/DEVELOPMENT.md` for prerequisites and the full coverage, diff coverage and dependency audit commands.
For documentation-only changes, check the diff, referenced paths and consistency with the code; Rust checks are not
required.

## CI/CD

- Every push to any branch runs: `rustfmt` check, `clippy` with warnings as errors, the test suite with coverage, diff
  coverage (`diff-cover` against `cargo llvm-cov`'s report: new/changed lines of `clipsync-core` and `clipsync-ffi`
  must be 100% covered, not just the project average), and `cargo-deny`. Pull requests reuse the checks of their head
  commit. When nothing but Markdown changed (a branch compared with `main` as a whole), the checks are skipped, and a
  skipped check counts as passed.
- Diff coverage applies to `clipsync-core` and `clipsync-ffi`; `clipsyncd`'s coverage is measured but not held to a
  threshold. That does not waive the requirement to test its behaviour changes.
- The Wayland tests start private headless Sway instances, so CI installs `sway` and `wl-clipboard`.
- Protection of `main`:
  - Nobody deletes `main` or force-pushes to it.
  - `main` only receives commits on which all of the above already passed. Nobody bypasses this.
  - Changes reach `main` through a pull request; only the repository owner may push to `main` directly.

## Commit Conventions

- Message format: `action: description` (e.g. `feat: description`, `fix: description`, `docs: description`,
  `test: description`, `ci: description`, `chore: description`).
- Group commits by logical change. Each commit should be independently understandable, buildable and testable.
  Leave unrelated changes untouched.
- When a pre-existing bug independent of the feature turns up during the work, commit the fix and its regression
  test as their own `fix:` commit, separate from the feature's `feat:` commit(s). Corrections to code introduced by
  the feature belong in that feature's commits.
- Each change gets its own short-lived branch off `main`. Follow Publication and Authorization to ship it.

## Publication and Authorization

- Committing locally and creating branches need no permission. Anything that publishes or lands code (pushing a
  branch, pushing to `main`, opening or merging a pull request) requires the user's explicit go-ahead for that specific
  action each time. A general "implement feature X" is not standing authorization to push or land it.
- "Push" authorizes pushing the branch only. "Open the PR" and "merge" authorize those respective actions.
  "Publish" authorizes the whole applicable landing sequence below, including pushing the branch, waiting for CI,
  landing on `main` and deleting the branch. For the PR path, this includes opening and merging the PR.
- Default path: push the branch, open a pull request and wait for CI. Land through the PR only with a method that
  preserves linear history and ensures the exact commit reaching `main` has already passed CI. A green PR head does
  not approve a different commit produced by squash, rebase or merge; any resulting commit must pass CI before
  landing. If the repository cannot enforce this for a merge method, do not use that method or bypass the rule.
  On GitHub, merge commits break linear history and squash or rebase merges always create new commits, so without a
  merge queue a pull request lands through the owner exception below: `main` is fast-forwarded to the PR's head,
  and GitHub marks the pull request as merged.
- Owner exception: only when acting for the repository owner with authorization to publish or push to `main`, push
  the branch, wait for CI on its head, then fast-forward `main` to that same commit with
  `git push origin <branch>:main`. Use this direct path only when authorized; it is not the default for contributors.
- For either path, if `main` advances and the branch needs rebasing, push the rebased branch and wait for CI on the
  new commit before landing. Delete the branch only after confirming it landed and when cleanup is authorized.

## Pull Request Conventions

These apply whenever a change goes through a pull request instead of a direct push.

- Title format: the same `action: description` as commits, naming the change as a whole.
- Description sections:
  - `## Summary`: the problem being solved, then what changed, as bullets.
  - `## Bugs found`: only for pre-existing, independent bugs fixed during the work, one bullet per bug, each fixed in
    its own `fix:` commit.
  - `## Tests`: what the new tests cover, then the full-suite result and whether `clippy`, `rustfmt`, diff coverage and
    `cargo-deny` are clean.
  - `## Manual verification`: only when something was checked by hand because CI cannot run it (e.g. the real
    Hyprland clipboard, a physical phone), saying what was checked and on what (compositor, Android version).
