# Architecture decisions

Short records of the choices that shape the project: what was decided, why, and
which alternatives were rejected, so they are not re-litigated without new
information. Some shape parts that are not built yet (the Android app); they
are recorded here because the reasoning has one home. When a decision changes, rewrite its entry to state the decision
in force.

## D1 — Linux side in Rust

Mature crates for the hard parts: `wayland-client` + `wayland-protocols(-wlr)`
for data-control, `x11rb` for a future X11 backend, `rustls`, `mdns-sd`, `ksni`
for a tray icon. One static binary with a small footprint suits an always-on
daemon.

Rejected: **Go** — no solid Wayland client library, so it would shell out to
`wl-paste --watch`, which is more fragile and cannot tell our own writes apart
from other apps' (needed for echo suppression).

## D2 — One protocol core in Rust, shared with Android through UniFFI

The protocol logic exists only in `clipsync-core`: framing, message
validation, the session state machine (hello and identity checks, both pairing
flows, keepalive, the duplicate-connection rule), SAS and clip ordering. The
Linux daemon links it directly; the Android app calls it through Kotlin
bindings generated by UniFFI, with the native library built by `cargo-ndk`.

The core is sans-IO, which is what makes sharing it work: each host does its
own I/O and feeds bytes and events in. On Android, Kotlin terminates TLS with
Keystore-backed keys (JSSE/Conscrypt) and hands the decrypted bytes to the
core, so the private key never leaves the Keystore. The core has no async
runtime and a synchronous API, so there is no async bridging, and UniFFI turns
Rust panics into Kotlin exceptions. It adds an estimated 1 MB per ABI to the
APK.

Costs accepted: the NDK, `cargo-ndk` and binding generation in the Android
build and CI; a linker flag for the 16 KB page alignment Android 15+ requires;
an F-Droid recipe that builds Rust; debugging across the FFI boundary.

Consequences:

- The public API of `clipsync-core` stays FFI-friendly: plain data types and
  enums across the boundary, errors as enums, no generics or lifetimes in
  exported items, synchronous calls, no I/O callbacks.
- Kotlin holds only platform code: TLS and the Keystore, NSD, the foreground
  service, the clipboard and the UI.

Rejected:

- **A second implementation in Kotlin**, kept in sync with the Rust one by
  shared test vectors. The session state machine, the hardest part of the
  protocol, would be written twice and re-synchronised on every protocol
  change, and test vectors pin deterministic functions well but sequences of
  states with timeouts poorly.
- **TLS in Rust**: the Keystore key cannot be exported, so it would mean either
  giving up hardware-backed keys or a rustls signer calling back into Kotlin
  on every handshake.

## D3 — Android platform code in native Kotlin

The difficult parts of the app (foreground service, NSD, Keystore, Quick
Settings tile, `PROCESS_TEXT`, share sheet) are platform APIs. Native Kotlin
with Jetpack Compose uses them directly; the protocol logic comes from the
shared core (D2).

Rejected: **Flutter** — it would only help with the UI and add a layer between
the app and every platform API it depends on.

## D4 — LAN-only peer-to-peer, mutual TLS with pinned keys

No server to run or trust. Identity is a P-256 key (not Ed25519, because the
Android Keystore only supports Ed25519 from API 33); peers pin each other's
SPKI hash at pairing time. Manual `host:port` also makes it work over
Tailscale or similar without extra code.

## D5 — Length-prefixed JSON frames

Only about ten small message types, so readability and trivial debugging beat a
binary encoding. Unknown types and fields are ignored for forward
compatibility. Binary payloads (images, files) will need their own frame kind.

## D6 — Lamport ordering for clips

Without ordering, two devices that copy at about the same time end up with each
other's text. A Lamport counter with a device-ID tie-break makes every device
converge on the same clip without trusting wall clocks. See spec §6.

## D7 — Android sends with one tap in v1

Since Android 10 only the focused app or the default keyboard can read the
clipboard. v1 accepts that: sending from Android uses the selection menu, the
share sheet, a Quick Settings tile or a notification action. Automatic reading
(Shizuku, `READ_LOGS`, custom keyboard) is out of scope for v1.

## D8 — Wayland data-control first

The first target is Omarchy/Hyprland. `ext-data-control-v1` (with
`wlr-data-control-unstable-v1` as fallback) also covers Sway, other wlroots
compositors and KDE Plasma. GNOME has neither protocol and X11 needs a
separate backend; both are out of scope for v1.

## D9 — Spec rules pinned by known-answer tests in the core

Every deterministic rule of `spec/protocol.md` (device ID, clip hash, framing
and message validation, clip ordering, SAS, pairing URI) has table-driven
known-answer tests in `clipsync-core`'s `tests/spec.rs`. Their expected values
(device IDs, digests, SAS codes) were computed by an independent
implementation of the spec and are kept as literals, never derived from the
code under test.

Rejected: **language-neutral JSON test vectors with a generator.** They pay off
when several implementations must agree; with a single shared core (D2) they
would only add a third language and a third place to change on every protocol
change.

## D10 — The clipboard at startup is not sent

When the daemon starts, whatever is already on the clipboard stays local; only
later changes are sent. Sending it would let a restart, a login or a crash
recovery on one device overwrite what the user just copied on another, with
nothing the user did to cause it. Copying the same text again is a new copy and
is sent.

Rejected: **sending it once the first peer connects** — the same surprise,
only later.
